2 · Spare memory means longer texts, more data or a larger model on the same free card

Base Soup uses 14,345 MiB of the card's 15 GB. Spare memory means longer texts, more data or a larger model on the same free card. We went after memory first, then time.

Approach

Same training task, less stored, less idle

1 · apply()

Guarded patches, no Soup mode

Every patch checks classes, dtypes and shapes; on a miss it runs the original code. A worker thread compiles our five kernels while Soup loads the model.

2 · 28 decoder layers

Real tokens only, fp16 where exact

Norms, residual adds and the MLP run on packed rows. NF4 weights are dequantized by K1; q, k and v are one GEMM. Add + RMSNorm is one Triton kernel, K3. Attention keeps the base shape so dropout masks match.

3 · LM head

Loss without the logits

K2 walks the vocabulary in tiles with online softmax and feeds Soup's own ChunkedStep protocol. The [B, T, V] logits never exist. The head is read from an exact fp16 copy.

4 · Backward

Rebuild instead of store

MLP gate and up, attention, dropout masks and LoRA inputs are recomputed from what autograd already keeps. Our own autograd code, not a Soup switch.

Compile time counts in the measured run: one launcher signature for all kernels (C1), our own SwiGLU kernel (C2) and the compile thread take step 1 from 5.1 s to 1.1 s.

3 · All kernel code is ours; ideas credited in the README

Same training task, less stored. Autograd stores inputs where it can, and backward rebuilds the rest. Padding is skipped. No Soup mode is used. Kernels compile on a worker thread during model load.

Components 1 to 3

Three Triton kernels do the heavy lifting

K1

NF4 dequantization

One 32-bit load per thread, four packed values; the NF4 table is a tree of 15 selects. Output equals bitsandbytes bit for bit.

0.166 ms against 0.300 ms on an [8960, 1536] weight.

K2

LM head + cross entropy

The vocabulary is walked in tiles with per-row online softmax; backward rebuilds each tile into the logits gradient in place. Entropy and accuracy go to Soup's ChunkedStep.

The full [B, T, V] logits never exist.

K3

Fused add + RMSNorm

One program per row, forward and backward; the backward also adds the residual gradient. Since v10b it also writes the fp16 copies the MLP GEMMs need and runs the LoRA epilogue.

About 500 small torch launches per step gone.

K2 and K3 together took the peak from 10,383 to 5,845 MiB (measured together). Ideas: bitsandbytes layout, Liger-Kernel and Unsloth (fused norm, chunked loss), online softmax (Milakov and Gimelshein, 2018). Read for ideas, not imported.

4 · Plus our own SwiGLU kernel, which repeats the starter example's math and is not counted toward the 5% rule

Three Triton kernels do the heavy lifting. K1 matches bitsandbytes bit for bit. K2 never builds the full logits. K3 fuses residual add and RMSNorm, and with P2 also small casts and the LoRA epilogue. All code is ours.

Honest ledger

What we tried and dropped

Per-row causal attention

Attention GPU time fell by about 40%, wall time did not move: 62.93 s without, 63.17 s with, same session. About 1,700 extra CPU-side operations per step made the step CPU-bound.

MLP recompute off on first layers

No speed gain beyond noise (71.95 s all on; 72.39 and 70.65 s with 7 off; 71.70 s with 2 off) for 340 MiB more peak.

Chunked MLP backward

40 MiB less for about 0.5 s more, and the only change that was not bit-exact: chunked cuBLAS GEMMs differ in the last bits at some row counts. Left in the code, off.

Compile pool inside apply()

Step 1 fell from 3.6 s to 1.0 s, but apply() grew by 2.8 s: the Triton frontend holds the GIL. Only overlapping the compile with model load pays, which is what v10d introduced and v11 ships.

Merged LoRA epilogue

About 0.15 s per run, below our bar of 5 ms per step. Dropped.

The v6 crash, fixed

Out of memory at step 22 of 64: a throw-away attention graph was kept alive by a pack hook, 0.5 GiB per step. Fixed in v6.1; a test now checks flat memory over 8 steps.

8 · Every number here is a Kaggle T4 measurement; details in results/measurements.md

Not everything worked. Per-row attention cut GPU time, not wall time. Compile in a pool inside apply only moved the cost. Chunked backward gained 40 MiB. The v6 leak is fixed in v6.1.

Limitations

Where the result is weaker

LimitWhat we measured
Session noiseBase time moves between 77 and 90 s across Kaggle sessions. Final repeats differ by 1.30 s (ours) and 2.70 s (base). Two full v9b runs gave s = 1.278 and 1.244. Compare ratios inside one session, not seconds across sessions.
Memory bought with timeMLP recompute, attention recompute and LoRA-input rebuild redo work in backward. In one session v9 took 69.85 s against 67.69 s for v8b, for 418 MiB less.
Part of the time is not oursThe GPU idles 100 to 180 ms per step in Soup and TRL host code: logging, rewind, NaN checks, optimizer. We did not change Soup; the overlap hides only the compile.
Scopefp16 on a T4, Qwen2 only. Under bf16 K1, K4, S4 and B fall back to the original code. K3 reorders the norm's fp32 sum by a few ulps; eval loss stayed within 0.003% of the base in every full run.
Example kernelOur SwiGLU repeats the starter example's math and may not count toward the 5% rule. Without it the own-kernel share was 9.8% at v7.
